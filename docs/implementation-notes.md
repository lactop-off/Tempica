# 実装メモ・設計確認事項

設計書 v1.0 に基づくバックエンド実装にあたっての決定事項・前提・残課題をまとめます。

## 確定した決定（ヒアリング済み）

| 項目 | 決定 | 備考 |
|---|---|---|
| 認証方式 | **HttpOnly セッション Cookie** | セッションは PostgreSQL に格納（`connect-pg-simple`、Redis 不要）。JWT は将来オプション |
| ライセンス | **Apache-2.0** | 特許条項あり。`LICENSE` / `NOTICE` を同梱 |
| 今回の実装範囲 | **MVP 中核を動作レベル** | 認証/組織/RBAC/打刻/集計/申請承認/勤務形態割当/月次締め/CSV。周辺は scaffold |

## 実装上の補足決定（設計書に明記が無く、妥当な既定で実装）

- **パスワードハッシュ**: `bcryptjs`（純 JS でビルド容易、自己ホスト配布性を優先）。argon2 への差し替えは将来検討。
- **RBAC の判定**: 1権限 = `feature × action × scope`。`scope` は `self < department < location < org`。
  `location`/`department` のデータ範囲は**部署ツリーの子孫**を解決して適用。
- **承認経路**: `approval_route` が無い場合は**単一ステップ**（scope で対象申請者が見える承認者なら誰でも可）。
  経路定義時は `steps[].approver_type='user'` で承認者を固定、それ以外は scope 判定。
- **自己承認の扱い**: 承認一覧からは**自分の申請を除外**（代理承認は将来、`approver_type` 拡張で対応）。
- **日次集計**: 打刻のたびに当日分を即時再計算。締め済み（`closed`）の日次は再計算しない。
- **深夜帯**: 既定 22:00〜翌5:00。`work_rule.overtime_rule` に将来パラメータ化可能。
- **休暇残数超過**: 設計どおり**警告のみ**（申請はブロックしない）。承認確定時に期限の近い残数から消化。
- **CSV 未締め混在**: 既定は **409 で拒否**。`organization.settings.csvAllowUnclosed = true` で許可に切替。
- **Shift_JIS 出力**: `iconv-lite` で対応。UTF-8 は BOM 付きで出力（Excel 互換）。
- **勤務形態の期間重複**: アプリ層で事前検証 + DB の **GiST EXCLUDE 制約**（`btree_gist`）で最終防衛。

## 設計書で気づいた残課題・確認推奨ポイント（実装はMVP既定で進行）

法令・運用に関わるため、社労士・運用設計と合わせて確定が望ましい項目です。
現状はプレースホルダ/既定値で動作し、設定や将来拡張で吸収できる作りにしています。

1. **残業区分の詳細**（法定内/外・36協定の月/年上限、割増率）: `work_rule.overtime_rule`(JSONB) に
   保持する想定だが、集計ロジックは現状「所定超過＝残業」の単純計算。区分集計（F-803）の詳細ルールは要確定。
2. **法定休日/所定休日の判定**: 休日判定の入力（会社カレンダー/曜日）が未定義。現状は申請/フラグ依存。
   休日マスタ（カレンダー）テーブルの追加を将来検討。
3. **有給の自動付与ルール**（F-602）: `leave_type.grant_rule`(JSONB) に保持する枠は用意済みだが、
   付与ロジック（入社日起算・勤続年数別日数・繰越）は未実装。バッチ（pg-boss）で実装予定。
4. **アラート（F-901/902）**: 36協定超過・有給取得義務の判定閾値が法令依存。通知基盤は実装済みのため、
   閾値とジョブの追加で対応可能。
5. **締め日と勤怠期間の対応**: `closing_period.close_day` はあるが、締め日が月末以外（例:20日締め）の
   場合の「対象期間」算出は現状「暦月」で簡略化。締め日基準の期間算出は要件確定後に拡張。
6. **シフト（F-701）の予実差異・希望→確定フロー**: 基本 CRUD は実装。ドラッグ編成や自動生成(F-702)は将来。
7. **通知の宛先解決**: 申請作成時の承認者への通知は、承認者が動的（scope 判定）なため現状は
   申請者本人への結果通知が中心。承認者一括通知は経路確定機能と合わせて拡張予定。

これらはいずれも MVP の動作を妨げないため、現段階では既定実装で先行し、要件確定後に段階的に詳細化します。
